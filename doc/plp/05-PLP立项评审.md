# PLP 立项评审：需求分析与 Carbon 实现方案评估

> 评审对象：《项目全生命周期运营管理平台立项报告 V1.0》（2026-09，数字化部）
> 评审视角：项目经理（范围、进度、成本、风险、干系人）
> 技术参照：Carbon（开源制造 ERP/MES，AGPL 核心 + 商业 EE），本机已部署并完成项目模块实测
> 结论时点：2026-11（距里程碑一仅数周，距里程碑二约 3 个月）

---

## 0. 结论先行

**建议采用"Carbon 作项目主干 + 专业系统各司其职"的混合方案，但立项报告需要改三处假设，否则 2027-06 的闭环目标不可达。**

| 判断 | 结论 |
| --- | --- |
| 需求真实性 | 高。四个问题诊断（无计划底座、移交无固化、过程无留痕、系统孤岛）与实际痛点吻合，且有量化证据（400+ 项目仅 1 个走完闭环、60 个字段重复填报） |
| 范围合理性 | **偏大**。五个板块 × 全流程 + 11 个系统集成 + 国内海外双模式 + 移动弱网 + 驾驶舱 + Agent，7 个月建成不现实 |
| Carbon 适配度 | **主干 80%，板块前端 50%，移动/驾驶舱 30%**。项目主数据、计划、里程碑、卡点、留痕、采购/库存/生产跟踪可复用；手续要件、招投标、现场施工、质保合同需二开或外挂 |
| 进度 | **里程碑二（2027-02）必须收敛范围**，否则会拖累后续全部里程碑 |
| 投入 | 全量约 45–55 人月；按 2027-06 前必须交付的范围裁剪后约 32–36 人月 |
| 决策 | 有条件 Go：先做 4 周 PoC（项目主干 + SAP/PDM 两条接口），PoC 通过再签外部开发合同 |

## 1. 立项报告解读（PM 视角）

### 1.1 范围一句话

以**项目主数据**为轴，把"经营计划 → 立项手续 → 招采供货 → 建设交付 → 售后运维"串成一条链，做到：一次建档、全链共用、节点卡卡、过程留痕、全景可视。

### 1.2 五大板块的能力清单（从报告提炼）

| 板块 | 必须建的能力 | 现有承载 | 报告验收口径 |
| --- | --- | --- | --- |
| 经营与计划 | 总体计划编制、里程碑、周进度自动汇总、资金付款与回款台账、项目复盘、经营驾驶舱 | 线下 + Excel | 周进度不再逐级人工汇报 |
| 立项与手续 | 线索-商机-立项、合同履约、八大局要件跟踪、国内/海外差异化审批 | eGo（线索）、OA（审批） | 要件进度可视；手续办结作为排产发运前置卡点 |
| 招采与供货 | 开工会、EPC/监理招标、采购与排产计划、生产进度、发运与到场签收 | 线下 + 简道云 | 与 SRM/SAP/MES 互通，全过程可查可溯可预警 |
| 建设与交付 | 施工节点跟踪、现场工单闭环、周报自动生成、调试并网验收、竣工移交、海外现场与知识库 | 简道云 | 国内全流程闭环；海外工单+备件台账 |
| 售后运维 | 竣工移交、故障工单、备品备件、质保合同关联 | 无系统 | 移交/工单/备件/质保全流程闭环 |
| 平台公共 | 架构选型、SSO、安全、分级权限、移动端（弱网离线）、数据底座 | 现有 IT | 移动端为现场主入口，弱网可离线填报 |

### 1.3 时间与里程碑（报告口径 + 我的可达性判断）

| 里程碑 | 计划 | 内容 | 可达性 | 建议 |
| --- | --- | --- | --- | --- |
| M1 总体方案评审 | 2026-11 | 架构、数据标准、接口规范 | ✅ 可达 | 保持，但需同时冻结"项目主数据字段字典"（60 字段） |
| M2 首批核心上线 | 2027-02 | 项目主数据 + 全链路流程 + 里程碑，支撑国内外销售/海外工程 | ⚠️ **风险最高** | 收缩为"主数据 + 计划/里程碑 + 项目看板 v0"，流程用现有 OA/eGo 承接 |
| M3 供应链贯通 | 2027-04 | 销售订单→主计划→采购→物料履约 | 🟡 有条件 | 依赖 SAP 接口（订单/库存/到货），需 2 月前冻结 |
| M4 全生命周期闭环 | 2027-06 | 国内工程 + 运维上线 | 🟡 有条件 | 现场施工与质保要提前二开，否则只能做"跟踪级" |
| M5 移动端 | 2027-09 | 审批、待办、进度、报工 | ⚠️ 弱网离线是硬缺口 | 拆成"移动审批（4 周）+ 现场离线（8 周）"两批 |
| M6 数据看板 | 2027-10 | 看板 + OTM/会议系统 | ✅ 可达 | 用只读副本 + BI，不占用业务库 |
| M7 智能 Agent | 2027-12 | 预警、任务推荐、资料检索 | 🟡 依赖数据质量 | 先做"检索 + 预警"，不做自动决策 |

### 1.4 组织与治理

- 四级组织（委员会 → 数字化建设部/PMO → 五板块组 → 外部开发）是合理的，**PMO 同时承担产品与开发**是最大人力风险。
- 报告的激励机制（奖金池、系数 0.4/0.2/0.2/0.2）解决了"业务不投入"这个头号风险，应保留。
- 缺一项治理安排：**数据主人（Data Owner）**。报告只说"谁产生谁维护"，没定"字段争议谁裁决"。建议在 M1 前把 60 个核心字段逐字段指定 owner。

### 1.5 指标（可直接作为验收）

流程线上化率 ≥95%、板块移交线上完成率 100%、关键节点留痕 100%、项目主数据统一率 100%、重复录入项清零、里程碑预警覆盖 100%、周进度系统自动汇总。

> PM 提醒：这五个指标里，"重复录入项清零"和"移交线上 100%"是**流程改造指标**，不是系统功能指标，验收要拉业务签字，不能只由 IT 演示。

## 2. 需求的真实复杂度

| 维度 | 数量级 | 含义 |
| --- | --- | --- |
| 板块 × 阶段 | 5 × 5 = 25 个流程域 | 每个域含表单、审批、附件、台账 |
| 板块交接点 | 约 8–10 个 | 每个都要"交接单 + 前置条件 + 双方确认" |
| 外部系统 | 11 个（eGo/OA/SAP/SRM/MES/PDM/WMS/OTM/成本/运维监控/简道云） | 平均每个 2–4 个接口 |
| 存量项目 | 400+ | 迁移 + 清洗 + 补录 |
| 重复字段 | 60 个 | 字段字典 + 口径统一 |
| 双模式 | 国内 + 海外 | 流程、单据、合规差异 |

**工作量结构估算**（全量口径）：流程与表单 40%、系统集成 25%、数据迁移 15%、报表看板 10%、移动端 10%。

## 3. Carbon 能力对照（fit / gap）

图例：✅ 原生可用 ｜ 🟡 配置即可 ｜ 🔧 需二开 ｜ 🚫 需外挂或自研

| PLP 需求 | Carbon 现状 | 判定 | 说明 |
| --- | --- | --- | --- |
| 项目一次建档、唯一编号 | `project.identifier` + 单据编号体系 | ✅ | 编号规则可配前缀 |
| 项目阶段进度条 | 元素树 + 里程碑 + 状态组 | 🟡 | 需把"五阶段"映射为元素/里程碑模板 |
| 标准计划模板按项目类型套用 | 项目模板 + 复制项目 | ✅ | 模板项目 → 复制即生成 |
| 里程碑定义与调整留痕 | `projectMilestone` + 基线 + 变更请求 | ✅ | 基线可对比 |
| 节点前置条件/卡点 | 计划锁、审批、权限 | 🔧 | 缺通用"卡点规则引擎"（条件+阻断+升级），需建 `gateRule/gateCheck` |
| 板块交接 | 审批流 + 项目元素评论 | 🔧 | 缺"交接单"实体（移交内容/人/时间/双签） |
| 过程资料归档 | `document` + 附件 + 变更历史 | 🟡 | 有文档对象，但版本控制与发放受控弱 |
| 周进度自动汇总 | 元素状态 + 工时 + 看板 | 🔧 | 需按"周报模板"聚合 |
| 延期/异常/变更审批 | 变更请求 + 审批规则（EE） | ✅/🟡 | 审批规则属商业版；可复用企业 OA |
| 资金付款计划/回款 | 合同、开票、收款 | 🔧 | 有财务单据，缺"付款计划/回款台账 + 预警"视图 |
| 项目复盘 | 无 | 🔧 | 建"复盘报告"对象，或挂在里程碑完成 |
| 经营驾驶舱 | 报表/导出 | 🚫 | 建议只读副本 + BI（Metabase/Superset） |
| 手续要件跟踪（八大局） | 无 | 🔧 | 最省的做法：要件作为"元素/任务 + 台账 + 卡点"，不建新引擎 |
| 招投标（EPC/监理） | 供应商询价/PO | 🚫 | 评标、标书、开标记录无模型 → 外挂或二期 |
| 采购/排产/生产/发运跟踪 | `purchaseOrder`、`job`、`shipment`、`itemLedger` | ✅ | 与 SAP 的分工见第 4 节 |
| 物料进度与项目进度匹配 | `projectElementMaterial` + `projectPeg` | 🟡 | 原生有供需配对，但缺"承诺日期 + 四节点"字段（需加 `materialCommitment`） |
| 现场施工工单 | 制造工单（`job`）+ 服务工单（`serviceJob`） | 🔧 | 施工工序/派单/验收需扩展或新建"现场工单" |
| 竣工移交 | 无 | 🔧 | 与"交接单"合并建模 |
| 售后：工单、备件、质保 | `serviceJob`、`customerAsset`、库存 | 🟡/🔧 | 工单与资产可用；**质保合同无模型**，需建 `warranty` |
| 移动审批/查询 | PWA（可装、推送） | ✅ | 现有安全可用 |
| 移动弱网离线填报 | 仅离线壳页，数据必须在线 | 🚫 | **硬缺口**，需自建离线草稿+补传队列（或选专门移动平台） |
| SSO / 分级权限 / 审计 | SSO、RLS、审计日志 | ✅ | 审计日志属 EE；社区版需自建审计视图 |
| 智能 Agent（预警/检索） | MCP + AI Agent（EE） | 🟡 | 能力在，但依赖数据质量与知识库 |

**总体适配度**：主干（主数据/计划/里程碑/卡点/留痕）约 80%；板块前端约 50%；移动与驾驶舱约 30%。

## 4. 推荐架构：Carbon 做主干，不试图做全部

```
┌─────────────────────────────────────────────────────────┐
│  PLP 前端（Carbon）                                      │
│  项目主干：主数据·编号·模板·计划/里程碑·交接·卡点·留痕    │
│  板块前端：手续台账 / 招采跟踪 / 供货跟踪 / 现场工单 / 售后 │
└───────────────┬──────────────────────────┬──────────────┘
                │ 项目号 / 单据号 / 状态     │ 只读副本
┌───────────────▼──────────────┐  ┌────────▼─────────────┐
│ 专业系统（SoR）               │  │ 数据层                │
│ SAP：订单·库存·成本·财务      │  │ BI 驾驶舱（Metabase） │
│ SRM：寻源·招标·合同          │  │ 数据底座（统一口径）   │
│ MES：制造执行                │  │ Agent（检索/预警）     │
│ PDM：BOM·图纸                │  └──────────────────────┘
│ WMS：备件仓储                │
│ OA/eGo：审批·获客            │
│ OTM：工时人效                │
└──────────────────────────────┘
```

### 4.1 三条必须写进方案的边界

1. **项目主数据归 PLP**（Carbon），订单/库存/成本/财务归 SAP，用项目号 + charge number 关联；
2. **PLP 不重算 MRP / 不做库存账**，只做"承诺与进度跟踪"（与上一轮 SAP 集成蓝图一致）；
3. **审批尽量复用 OA**，避免把 EE 审批流变成硬依赖，也符合报告"审批链路冗长"的诉求。

### 4.2 需要新建的四个模型（Carbon 侧）

| 模型 | 用途 | 工期 |
| --- | --- | --- |
| `handover`（交接单） | 板块间移交：内容、移交人、接收人、时间、双签、前置条件 | 3 周 |
| `gateRule/gateCheck`（卡点） | 规则配置、校验结果、阻断/升级、闭环 | 4 周 |
| `requirement/permit`（要件台账） | 八大局要件、状态、有效期、卡点引用 | 3 周 |
| `warranty`（质保合同） | 质保期、范围、免责、与服务工单绑定 | 3 周 |

现场施工工单建议在 `job` 上扩展"施工类型 + 派单 + 验收"，不另起一套；若差异过大再独立建模。

## 5. 关键缺口与对策（Top 5）

| # | 缺口 | 影响 | 最小可行对策 | 工期 |
| --- | --- | --- | --- | --- |
| 1 | 移动弱网离线 | 海外与现场是主场景，无离线=不可用 | 先做"移动审批+拍照+进度上报"（在线）；离线草稿单独立项（IndexedDB + 补传队列 + 冲突合并） | 8 周 |
| 2 | 交接与卡点引擎 | "移交无固化"是四大问题的核心 | 先做 4 个交接点（营销→供应链、供应链→工程、工程→运维、海外→属地）+ 6 条卡点规则 | 6 周 |
| 3 | 招投标 | EPC/监理招标是独立业务，模型复杂 | 一期只做"招标台账 + 合同挂接"，评标过程沿用现有方式 | 4 周 |
| 4 | 质保合同 | 售后闭环缺合同维度 | 建 `warranty` 轻模型，与服务工单/客户资产关联 | 3 周 |
| 5 | 驾驶舱 | 需要跨系统口径 | BI 接只读副本，指标口径由 PMO 与财务共同定义 | 4 周 |

## 9. 给决策层的五条建议

1. **批准立项，但修正范围**：五个板块分两批，2027-06 前只保证 P1–P4；移动、驾驶舱、Agent 明确放到下半年（与 M5–M7 一致）。
2. **先做 4 周 PoC**：Carbon 起项目主干，接通 PDM（BOM）与 SAP（订单/库存）两条接口，跑通一个真实项目。PoC 不通过就不签外部开发合同。
3. **字段字典先行**：60 个核心字段在 M1 前定 owner 与口径，这是"重复录入清零"的唯一抓手。
4. **交接与卡点作为一号工程**：它直接对应报告里的"结构性短板"，也是最能被业务感知的价值点。
5. **许可与运维单列预算**：EE（审批/工作流/门户/Agent）与自托管运维不要藏在开发费里。
