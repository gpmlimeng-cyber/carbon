系统集成详细方案

面向“系统集成 + 按项目交付”型储能企业的双系统蓝图：Carbon 承担业务界面与执行层（SoE）， SAP 承担核心业务逻辑与账（SoR），两者通过契约化接口集成——每个单据只有一个状态机主人。

01执行摘要

这套方案不是“两套 ERP 并联”，而是一次明确的职责切分：SAP 是账，Carbon 是手和眼。 前台把报价、配置、车间、质量、售后做得好用；后台把订单、库存、成本、发票管得准确。中间的接口层 负责“让两边说的是同一件事”。

结论

  • 可行性高：Carbon 已有 /api/v1（OpenAPI）、出站 Webhook、19 条入站 Webhook、工作流引擎与集成连接表，做“前台 + 集成”不需要改核心。
  • 风险集中在边界：真正会失败的不是技术，而是“谁改状态、谁算成本、谁建生产订单”没定死。
  • 投入结构：Carbon 二开 14 人月、集成层 10 人月、SAP 侧 6–10 人月、双跑测试 6 人月。

三个必须本周定掉的决策

① 生产订单归属

SAP 建单、Carbon 执行并回传确认（推荐）；反过来则要重写 SAP 的 PP 集成，成本翻倍。

② 工程 BOM 归属

Carbon 拥有 EBOM 与项目配置，SAP 拥有 MBOM/工艺路线；通过“发布”单向同步。

③ 序列号粒度

SAP 管到设备级（柜/簇），电芯级血缘放 Carbon；否则 SAP SER 表会被电芯撑爆。

03架构原则与铁律

原则不是口号，是评审时用来驳回设计的依据。以下四条铁律，违反任何一条，集成的长期成本都会超过重做。

铁律 1 · 单一状态机

同一业务对象（销售订单 / 采购订单 / 生产订单 / 库存 / 发票）只有一方能改状态，另一方只读镜像并展示来源。Carbon 侧的状态字段由接口写入，界面不可直接编辑。

铁律 2 · 单一账本

库存数量与金额只存在于 SAP。Carbon 不计库存账、不做成本结转、不出财务凭证；所有库存变动都是“向 SAP 提交的移动请求”。

铁律 3 · 单一主数据源

物料、客户、供应商、工厂、库位、工作中心以 SAP 为准，Carbon 只读并建本地索引；Carbon 需要新物料时走“主数据申请单”，由接口在 SAP 创建后回传编号。

铁律 4 · 写操作必带幂等键，失败必进死信

Carbon 的每一次跨系统写都必须携带业务幂等键（类型 + 单据 + 版本），失败进入死信队列并可人工重放；禁止“无限重试”和“静默吞错”。

六条设计原则

原则含义落地约束
查缓存、写排队读走缓存 + 短 TTL；写走 outbox，前台不阻塞在 SAP 上查询 800ms 超时；写 2s 超时转异步
契约先行接口先有 OpenAPI/IDoc 契约与样例报文，再写代码契约仓库 + 契约测试进 CI
一字段一主人每个字段只有一个系统可写，另一侧只读字段级 owner 清单（见 §4.2）
可观测每个跨系统操作有 correlationId、耗时、结果两侧日志可按同一 ID 串联
可降级SAP 不可用时前台进入只读 + 排队，而不是白屏降级开关 + 横幅提示 + 队列积压告警
可对账没有对账的集成等于没有集成日对账 + 差异表 + 责任人

05集成架构

三条通道各司其职：查走缓存、关键写走同步、批量写走异步。任何一条通道被滥用，都会在半年内变成性能或一致性事故。

5.1 三条通道

通道用途典型对象与接口约束
A 同步查询
OData GET		 前台读：物料、库存、订单状态、成本汇总 API_PRODUCT_SRV · API_MATERIAL_STOCK_SRV · API_SALES_ORDER_SRV 必须缓存（30–60s）+ 800ms 超时；超时回缓存并标注“数据时间”
B 同步写
OData POST / BAPI		 少量、需即时结果：销售订单、生产订单确认 API_SALES_ORDER_SRV · API_PRODORDER_CONFIRMATION 2s 超时；超时自动转 outbox 并提示“处理中”
C 异步批量
IDoc / 队列		 大批量、可延迟：收货、库存移动、发票 WMMBID02 · API_MATERIAL_DOCUMENT_SRV · 发票 IDoc 幂等 + 日对账；夜间窗口优先，单批 ≤500 行
禁止事项

① Carbon 直连 SAP 数据库或 RFC 直连绕过网关；② SAP 回调 Carbon 的私有接口（只能走网关或事件）；③ 用“全量同步”代替增量（物料主数据每天全量会把 SAP 拖死）；④ 在 Carbon 内做库存结存或成本结转。

6.1 契约规范

  • 每个接口一份契约：openapi.yaml（OData 场景）或 idoc-<name>.md（IDoc 场景）+ 样例报文 + 字段映射表。
  • 契约变更走评审：字段新增向后兼容，字段删除需双写过渡期（≥1 个版本）。
  • 契约测试进 CI：用录制报文做回放，防止 SAP 升级后静默变更。
  • 错误码字典：SAP 业务错误（4xx/消息号）必须映射为用户可读中文，原始消息号保留在日志。

07主数据与 ID 治理

双系统集成 80% 的“数据不对”，根因都在主数据与标识。映射表是地基，必须先建。

7.1 双 ID 与映射表

CREATE TABLE "sapObjectMap" (
  id            text PRIMARY KEY DEFAULT xid(),
  "companyId"   text NOT NULL,
  "objectType"  text NOT NULL,         -- material/customer/so/po/prodOrder/serial...
  "carbonId"    text NOT NULL,
  "sapKey"      text NOT NULL,         -- SAP 业务编号（保留前导零）
  "sapSystem"   text NOT NULL,         -- 多客户端/多公司码时区分
  "validFrom"   timestamptz NOT NULL DEFAULT now(),
  "validTo"     timestamptz,           -- 失效不删，保留历史
  UNIQUE ("companyId","objectType","carbonId","sapSystem","validFrom")
);
CREATE INDEX ON "sapObjectMap" ("objectType","sapKey");

7.2 SAP 特有的七个坑

坑表现处理
前导零物料号 10023 与 0000000000010023 匹配不上统一 padStart(18,'0') 存储，展示去零
单位双码SAP 内部单位 ST vs ISO PCE单位映射表 + 换算因子，禁止两处各存一套
金额精度packed decimal 与 JS float 不一致，差几分钱统一 numeric(19,6)，传输用字符串
日期格式/Date(1731000000000)/网关统一转 ISO8601
时区单据日期与过账日期混淆分别存储，界面标注“过账日”
多公司码/工厂报文缺 plant 导致过账到错工厂每条报文强制带 companyCode/plant
删除/冻结deletion flag ≠ 物理删除Carbon 侧只做“不可选”，历史单不删

7.3 主数据同步策略

对象策略频率说明
物料增量（LastChangedAt）+ 夜间全量校验15min / 1d只同步本工厂相关视图，减少 90% 数据量
客户/供应商增量15min只同步已启用 + 有交易的对象
BOM / 工艺按需拉取（进入工单时）实时全量同步代价高，按单拉取 + 短缓存
库存查询时读 + 60s 缓存实时不落地，避免“两套库存数”
序列号增量15min只同步已交付/在制设备级，不含电芯级
主数据申请闭环

Carbon 发起“新建物料/客户”申请 → 网关落 SAP 申请表 → SAP 审批建码 → 事件回传 → Carbon 自动补全映射。全程可查，不允许“先在 Carbon 建一个临时码，以后再说”——临时码是双系统集成的第一颗雷。

08一致性与事务

跨系统没有分布式事务。方案是：本地事务 + outbox + 幂等 + 对账，用工程手段换取最终一致。

8.1 三种交互模式

模式适用机制用户体验
查 · Cache-Aside物料、库存、订单状态读 Redis（TTL 30–60s），miss 才调 SAP；stale-while-revalidate首屏快；显示“数据截至 HH:mm”
写 · Outbox报工、移动、开票申请本地事务写 outbox → 异步调 SAP → 回写状态提交即成功（本地），角标显示同步状态
写 · Write-Through销售订单创建、生产确认同步调 SAP，2s 超时；超时转 outbox显示 SAP 单号或“处理中”

8.2 outbox 表与状态机

CREATE TABLE "sapOutbox" (
  id              text PRIMARY KEY DEFAULT xid(),
  "objectType"    text NOT NULL,
  "carbonId"      text NOT NULL,
  "idempotencyKey" text NOT NULL UNIQUE,
  payload         jsonb NOT NULL,   -- 已转成 SAP 契约
  status          text NOT NULL DEFAULT 'Pending',
                  -- Pending/Sending/Synced/Failed/Dead
  attempts        int  NOT NULL DEFAULT 0,
  "sapKey"        text,
  "lastError"     text,
  "nextAttemptAt" timestamptz,
  "createdAt"     timestamptz NOT NULL DEFAULT now()
);

8.3 失败处理策略

场景判定处理
SAP 业务拒绝4xx / 消息号 E 类不重试；标记 Failed；UI 展示中文解释 + 原始消息号
超时 / 5xx / 限流HTTP 408/429/5xx指数退避（1s→2s→…→5min，≤10 次）；仍失败进 Dead
重复提交同幂等键已存在返回既有 sapKey（幂等成功，不算错误）
SAP 长时不可用连续 5 分钟失败率 >50%降级为“只读 + 排队”；顶部横幅；禁止新建跨系统单据
部分成功批量 IDoc 中部分行失败按行记录结果，失败行进 Dead，成功行不回滚

8.4 对账（没有对账就没有集成）

日对账

按对象比对“Carbon 已提交”与“SAP 已存在”，差异写 reconDiff 并指派责任人。

状态对账

SAP 状态变化必须回刷 Carbon：事件优先，轮询兜底（15min）。

金额对账

开票/收货金额与 SAP 凭证核对，月度财务签字，差异有台账。

09关键场景时序

9.1 销售订单：报价 → SAP 订单

1
Carbon 报价与配置确认校验客户信用占位、物料可售、交期可行性（数据来自 SAP 缓存）
2
提交订单（I-05）网关 → API_SALES_ORDER_SRV deep insert，携带幂等键 SO:{id}:v1
3
SAP 返回订单号Carbon 写映射表、状态 Synced，页面展示 SAP 单号
4
后续变更回传（I-06）事件优先；轮询兜底；Carbon 只更新镜像字段，不允许本地改状态

9.2 车间执行：SAP 生产订单 → Carbon 执行 → 回传确认

1
SAP 下发生产订单（I-09）订单号、组件需求、工序顺序、计划日期 → Carbon 生成执行单
2
扫码开工 / 报工操作员扫工单码与料码，录入数量、工时、废品；SN 父子关系在本地建立
3
回传确认（I-10）outbox → API_PRODORDER_CONFIRMATION；成功回写确认号
4
EOL 检验（I-12）测量值入库；结果回写 SAP 检验批，触发使用决策

9.3 收货与库存移动：Carbon 发起，SAP 记账

1
仓管扫码收货PO、行号、批次、SN、数量；本地先校验（不重复、不超收）
2
写 outbox（I-08）幂等键 MVT:{id}，负载转成物料凭证报文（101/105）
3
SAP 过账返回物料凭证号；Carbon 回写并失效该物料+库位的库存缓存
4
日对账数量与金额双向核对，差异进 reconDiff

9.4 项目成本：只读，不重算

硬约束

Carbon 不计算项目成本。项目毛利 = SAP 开票收入 − SAP 成本归集（材料 + 人工 + 外协 + 费用），按 WBS 汇总，每日同步一次。Carbon 侧只做展示与钻取，任何“帮 SAP 算一遍”的设计都必须驳回。

15架构决策记录

ADR-07
SAP 为 SoR，Carbon 为 SoE
备选
双主 / Carbon 为主 / SAP 为主
理由
账面必须单一；前台价值在体验与执行速度，与账务强一致无必然关系
影响
Carbon 所有状态字段只读镜像；写操作均为“请求”
ADR-08
一字段一 owner，单向同步
备选
双向同步 / 以时间戳决胜
理由
双向必然冲突且无法定责；时间戳决胜在时钟漂移下不可靠
影响
需要字段级 owner 清单并进评审
ADR-09
Carbon 拥有 EBOM/配置与 SN 血缘
备选
全部放 SAP
理由
SAP 的工程 BOM 与多级血缘表达能力弱，改造成本高于双系统
影响
发布流程：Carbon 冻结配置 → 生成 SAP MBOM/组件
ADR-10
关键单据同步写，其余 outbox
备选
全同步 / 全异步 / 人工批量
理由
兼顾 UX 与 SAP 限流；全同步在车间高峰期会打爆接口
影响
需要 outbox 表、死信页与状态角标
ADR-11
中间件优先用 SAP Integration Suite
备选
自研直连 / 开源 ESB
理由
限流、转换、监控、审计开箱即用；自研只作兜底
影响
需要 BTP/IS 许可；无许可则评估自研网关
ADR-12
追溯查询统一在 Carbon
备选
两个入口 / 以 SAP 为入口
理由
用户只需一个入口；Carbon 同时拥有血缘与 SAP 状态
影响
查询页需聚合两源并标注数据时间

16.2 立项评审必答的 8 个问题

  1. SAP 版本与模块范围（S/4 或 ECC；PP/QM/PS/CO 是否已启用）？
  2. 物料主数据是否已有工厂视图与批次/序列号管理？
  3. 生产订单谁建（SAP 建、Carbon 执行，还是反过来）？
  4. 序列号粒度：SAP 到设备级还是电芯级？
  5. 是否有 SAP BTP / Integration Suite 许可？无许可的替代方案与成本？
  6. PS 的 WBS 结构能否承载“项目 → 多机柜”的层级？
  7. 开票是否必须在 SAP（多数是），Carbon 只做申请？
  8. 网络与账号：链路、技术账号、证书、限流配额是否已与 BASIS 对齐？
